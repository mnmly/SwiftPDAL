  1. Bugs / Safety Issues

  PointCloudChunk.data is a dangling pointer

  SwiftPDAL.swift:243-245 — The data computed property calls withUnsafeBytes and returns the pointer outside the closure's lifetime. This is undefined behavior — the pointer is only valid inside the closure.

  // BROKEN: pointer escapes withUnsafeBytes scope
  public var data: UnsafeRawPointer {
      ownedData.withUnsafeBytes { $0.baseAddress! }
  }

  Fix: either expose ownedData directly for callers to use withUnsafeBytes, or store the data in a contiguous allocation you control (e.g. UnsafeMutableRawBufferPointer).

  StreamingPointCloud.data force-unwraps a null pointer

  SwiftPDAL.swift:313 — UnsafeRawPointer(bitPattern: 0)! is guaranteed to crash — bitPattern 0 produces nil.

  return UnsafeRawPointer(bitPattern: 0)!  // 💥 always crashes

  This should either return an Optional or fatalError with a meaningful message.

  Bounds.transformed only transforms 2 of 8 corners

  SwiftPDAL.swift:24-49 — For a general transformation (rotation, shear), you need to transform all 8 AABB corners and take the min/max. Transforming only min+max gives wrong results for anything beyond
  translation+uniform-scale.

  Duplicate bounds reads in streamCallback

  pdal_wrapper.cpp:595-607 — The streamCallback method reads X/Y/Z twice per point: once for bounds tracking (lines 595–603) and again in the dimension loop (lines 612–616). The bounds-tracking reads at lines
  605-607 are completely redundant (the values were already read at 595-597 and aren't used after).

  #define PDAL_DIM with no value

  pdal_wrapper.h:31 — There's a dangling #define PDAL_DIM that seems like it should be PDAL_DIM_SCAN_DIRECTION (1 << 10). It shadows nothing useful and will break any code that uses it.

  2. C++/Swift Interop Improvements

  Expose C++ types as Swift reference types with SWIFT_SHARED_REFERENCE

  The PDALPointViewPtr / PointViewContext pattern uses raw void* opaque pointers with manual new/delete and Unmanaged bridging. Since you're on Swift 6.2 with Cxx interop, you can annotate PointViewContext with
  SWIFT_SHARED_REFERENCE and get automatic reference-counted lifetime management in Swift:

  #include <swift/bridging>

  struct PointViewContext {
      // ...
  } SWIFT_SHARED_REFERENCE(retainPointViewContext, releasePointViewContext);

  void retainPointViewContext(PointViewContext* ctx);
  void releasePointViewContext(PointViewContext* ctx);

  This eliminates the Unmanaged dance in StreamingPointCloud and the manual deinit/pdal_free_point_view calls.

  Replace hand-rolled JSON parser with nlohmann/json or just use the C++ side differently

  pdal_wrapper.cpp:110-148 — DimensionMapper has a fragile hand-rolled JSON parser that won't handle escaped quotes, nested objects, or unicode. Since the JSON is generated by Swift's JSONEncoder, consider either:
  - Using a proper JSON library on the C++ side, or
  - Passing the dimension map as a flat array of C string pairs instead of JSON, avoiding serialization entirely.

  Callback pattern could use SWIFT_NONCOPYABLE or avoid Unmanaged

  The CallbackBox / CallbackContext / Unmanaged.passRetained pattern (SwiftPDAL.swift:485-543 and duplicated at 585-638) is complex and duplicated. Two improvements:
  1. Extract a shared helper — both readStreamingInternal and readStreamingFromView have identical CallbackBox/CallbackContext classes.
  2. Consider passing a Swift closure directly through the context pointer using a simpler withoutActuallyEscaping + UnsafeMutablePointer<Closure> pattern.

  std::string parameters in the C API

  pdal_wrapper.h:62,91,109,127 — The public C API functions take const std::string& parameters, which means Swift must construct std.string at every call site. Since this is a C-interop boundary, prefer const char*
  for simpler bridging and wider compatibility:

  // Before
  int pdal_read_binary(const std::string& reader_name_backup, const std::string& filename, ...);

  // After
  int pdal_read_binary(const char* reader_name_backup, const char* filename, ...);

  This also makes the API usable from pure C (the header already includes C types like PDALPipeline as void*).

  3. Memory & Resource Management

  PointCloud cleanup is easy to forget

  PointCloud is a struct with manual cleanup(). If a caller forgets to call it, memory leaks. Consider:
  - Making it a class with deinit, or
  - Using ~Copyable (Swift 5.9+) with a deinit to enforce single-ownership semantics and automatic cleanup:

  public struct PointCloud: ~Copyable, PointCloudData {
      // ...
      deinit { pdal_free_data(...) }
  }

  StreamingPointCloud.makeBuffer ignores the options parameter

  SwiftPDAL.swift:459-464 — The method accepts options but immediately shadows it with .storageModeShared:

  public func makeBuffer(device: any MTLDevice, options: MTLResourceOptions) -> (any MTLBuffer)? {
      let options: MTLResourceOptions = .storageModeShared  // shadows parameter!
      mtlBuffer = device.makeBuffer(length: totalByteLength, options: options)

  setenv calls are not thread-safe

  PROJ_DATA and PDAL_DRIVER_PATH are set via setenv in read() and loadInfo(). If two threads read different files concurrently, these environment variables could race. Consider setting them once at initialization or
   using a dispatch_once equivalent.

  4. API Design

  PointCloudData protocol requires UnsafeRawPointer but StreamingPointCloud doesn't have one

  StreamingPointCloud.data returns either mtlBuffer.contents() or crashes (null pointer). The protocol isn't a natural fit — streaming data arrives in chunks, not as a single contiguous buffer. Consider splitting
  the protocol or making data optional.

  Error codes are magic numbers

  Both C++ and Swift duplicate error-code-to-message mapping (SwiftPDAL.swift:557-568, 648-658). Define an enum or constants in the header:

  enum PDALError {
      PDAL_OK = 0,
      PDAL_ERR_NOT_IMPLEMENTED = -1,
      PDAL_ERR_PDAL = -2,
      // ...
  };

  readerName default is misleading

  The default readerName: String = "readers.text" appears throughout, but it's actually a fallback — StageFactory.inferReaderDriver() usually picks the correct reader from the file extension. The parameter name
  should reflect this (e.g., fallbackReader).

  5. Code Duplication

  - Dimension spec creation is duplicated between createDimensionSpecs() (line 279) and ProgressivePointLoader::initialize() (line 524). Extract a shared function.
  - CallbackBox/CallbackContext pattern is copy-pasted between readStreamingInternal and readStreamingFromView.
  - DimensionInfo extensions (SwiftPDAL.swift:796-858) duplicate the same computed properties on both PDALDimensionInfo and DimensionInfo. If DimensionInfo is the Swift-side type, consider dropping the extension on
  PDALDimensionInfo or having one delegate to the other.
